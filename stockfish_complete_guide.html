1. What IS a Chess Engine?

A chess engine is a program that analyzes chess positions and finds the best move. Think of it like a chess grandmaster inside your computer — except it can look at millions of positions per second.

At its core, every chess engine does two things:

  1. Search — Look ahead at possible future moves (like a tree of possibilities)
  2. Evaluate — Judge how good each resulting position is

Stockfish is the world's strongest open-source chess engine. It uses a combination of incredibly efficient search algorithms and a neural network (NNUE) for evaluation. As of 2026 (Stockfish 18), it's estimated at ~3600+ Elo — far beyond any human grandmaster (~2800).

The Analogy

Imagine you're playing chess. You think: "If I move my knight here, they'll probably take my bishop, then I'll push my pawn..."

A chess engine does exactly this, but it considers every legal move, not just the "obvious" ones. And it does this millions of times per second, looking 20-40 moves ahead.

You → Move A → They respond → You respond → ... → Position (good? bad?) → Move B → They respond → You respond → ... → Position (good? bad?) → Move C → ... → Move D → ... This forms a TREE. The engine explores this tree.

3. Board Representation — Bitboards

Stockfish uses bitboards — 64-bit integers where each bit represents one square of the chess board. Since a chess board has exactly 64 squares, one uint64_t can represent "which squares have white pawns on them", or "which squares are attacked by the black queen".

Why Bitboards Are Brilliant

With bitboards, complex chess operations become simple CPU operations:

// "Where are all squares attacked by white pawns?" // Just shift the pawn bitboard and use OR! Bitboard whitePawnAttacks = (whitePawns << 7) | (whitePawns << 9); // "Are any of my pieces attacked by their pawns?" Bitboard danger = myPieces & theirPawnAttacks; // AND operation! // "How many pieces does white have?" int count = __builtin_popcountll(whitePieces); // POPCNT instruction!

What Stockfish Stores (in position.h)

  • byTypeBB[7] — One bitboard per piece type (Pawn, Knight, Bishop, Rook, Queen, King, ALL_PIECES)
  • byColorBB[2] — One bitboard per color (White, Black)
  • board[64] — For each square, what piece is on it (quick lookup)

Magic Bitboards for Sliding Pieces

Bishops and rooks "slide" along lines, and their attacks depend on what's blocking them. Computing this naively is slow. Stockfish uses Magic Bitboards: precomputed lookup tables that use a "magic number" multiplication + shift to find the right attack pattern instantly.

On modern CPUs with BMI2, Stockfish can use the PEXT (Parallel Bit Extract) instruction instead of magic multiplication — even faster.

4. Move Generation

Move generation (movegen.cpp) produces all legal or pseudo-legal moves in a position. Stockfish generates moves in stages to avoid generating all moves upfront (most will never be needed due to beta cutoffs).

Move Encoding

Each move is packed into a 16-bit integer:

Bits 0-5: Destination square (0-63) Bits 6-11: Source square (0-63) Bits 12-13: Promotion piece type (Knight=0, Bishop=1, Rook=2, Queen=3) Bits 14-15: Special flags (Normal=0, Promotion=1, En-passant=2, Castling=3)

5. The Search Algorithm — Finding the Best Move

This is the heart of Stockfish. The file search.cpp (~1700 lines) implements the most sophisticated alpha-beta search in existence, with dozens of pruning and reduction techniques.

5.1 Alpha-Beta Pruning (The Foundation)

Alpha-beta is an optimization of minimax search. In minimax, you evaluate every leaf node. Alpha-beta lets you skip entire branches that can't possibly affect the result.

Minimax: "I need to check ALL possibilities" Alpha-Beta: "Wait — I already know I can get +2 from another branch. This branch can at most give +1. SKIP IT!" Alpha = best score I can guarantee (lower bound) Beta = best score opponent can guarantee (upper bound) If alpha >= beta → CUTOFF (prune this branch)

5.2 Iterative Deepening

Instead of searching directly to depth 30, Stockfish searches to depth 1, then 2, then 3, etc. This sounds wasteful but is actually faster because:

  • The transposition table caches results from shallower searches
  • Move ordering improves with each iteration (best moves from depth N help at depth N+1)
  • You can stop anytime and still have a valid best move
  • Time management can decide when to stop

5.3 Aspiration Windows

At each new depth, instead of searching with the full range [-infinity, +infinity], Stockfish uses a narrow window around the expected score. If the result falls outside, it re-searches with a wider window.

// Initial window: score ± delta (delta starts at 5 + threadIdx % 8) alpha = averageScore - delta; beta = averageScore + delta; // If search fails outside window, expand: delta += delta / 3; // Re-search with wider window

5.4 Pruning Techniques (The Secret Sauce)

Pruning means skipping moves/positions that are unlikely to matter. This is how Stockfish searches so deep — it only fully examines important moves.

Null Move Pruning (Step 9)

Idea: "If I do NOTHING (pass my turn) and I'm STILL winning by a lot, then this position is clearly good for me — no need to search deeper."

How: Make a "null move" (skip your turn), search with reduced depth. If the score is still >= beta, prune.

Reduction: R = 7 + depth/3 (aggressive!)

Safety: Verification search at high depths to avoid zugzwang traps.

Late Move Reductions (LMR) (Step 15)

Idea: "The first few moves are usually the most important (thanks to good move ordering). Later moves are less likely to be the best, so search them at reduced depth."

How: After the first few moves, reduce the search depth. If a reduced search returns a surprisingly good score, re-search at full depth.

// Reduction formula (per-thread variation via lmrDivisor): reductions[i] = int(2763 / 128.0 * log(i)); // reduction() function considers: // - improving: less reduction if position is getting better // - depth: more reduction at high depths // - moveCount: more reduction for later moves // - delta: window size affects reduction

Razoring (Step 7)

Idea: "If the static eval is REALLY far below alpha, this position is hopeless. Just do quiescence search and return."

Threshold: eval < alpha - 502 - 306×depth²

Futility Pruning (Step 8)

Idea: "If the eval is well above beta and there's no TT move, it's unlikely any move will change the outcome. Return early."

ProbCut (Step 11)

Idea: "If a shallow search of captures finds a score way above beta, the full search probably will too. Prune."

Threshold: probCutBeta = beta + 224 - 61×improving

SEE Pruning (Step 14)

Idea: "If a capture is a clearly losing exchange (e.g., trading queen for pawn), skip it at shallow depths."

SEE = Static Exchange Evaluation — a fast way to evaluate a series of captures on one square.

5.5 Extensions

Sometimes you MUST search deeper (not reduce). Extensions add depth for critical moves:

  • Singular Extension: If one move is significantly better than all others, extend its search
  • Check Extension: When giving check, extend to see the consequences
  • Recapture Extension: Extend recaptures to resolve tactical sequences

5.6 Quiescence Search (qsearch)

At the "leaves" of the search tree (depth ≤ 0), positions can be unstable — a hanging piece might be about to be captured. Quiescence search continues searching only captures and checks until the position is "quiet".

This prevents the "horizon effect" — where the engine thinks a position is good because it can't see the opponent's winning capture just beyond its search depth.

6. NNUE — The Neural Network Brain

NNUE (Efficiently Updatable Neural Networks) is Stockfish's evaluation function. Instead of hand-crafted rules ("bishops are worth 3.25 pawns", "doubled pawns are bad"), NNUE uses a trained neural network to assess positions.

NNUE was originally developed for Shogi (Japanese chess) by Yu Nasu in 2018, and was integrated into Stockfish in 2020, providing a massive ~80 Elo jump.

6.1 Why "Efficiently Updatable"?

The key insight: when you make a chess move, only 2-4 pieces change position. Instead of re-evaluating the entire network from scratch, you can incrementally update only the affected weights. This makes NNUE fast enough to call millions of times per second during search.

6.2 Network Architecture (SFNNv8+)

INPUT FEATURES (587,760 dimensions) ├── HalfKAv2_hm: 527,040 dims (king-piece features with horizontal mirroring) └── FullThreats: 60,720 dims (piece-threat features) ↓ ┌────────────────────────────────────┐ │ FEATURE TRANSFORMER (L1) │ │ 587,760 → 1024 neurons │ │ (This is the "accumulator") │ │ Two perspectives: White + Black │ │ = 2 × 1024 neurons │ └────────────┬───────────────────────┘ ↓ ┌────────┴────────┐ │ SqrClippedReLU │ ClippedReLU │ (squared) │ (normal) └────────┬────────┘────┘ ↓ concatenated ┌────────────────────────────────────┐ │ HIDDEN LAYER (L2): 31 neurons │ │ (8 LayerStacks — one per │ │ material count bucket) │ └────────────┬───────────────────────┘ ↓ ClippedReLU ┌────────────────────────────────────┐ │ OUTPUT LAYER (L3): 32 neurons │ │ → Single evaluation score │ └────────────────────────────────────┘

6.3 Feature Inputs Explained

HalfKAv2_hm (King-Piece features)

For each perspective (White/Black), the features encode:

  • Which square is my king on? (factored into "king buckets" — groups of similar squares)
  • For each other piece on the board: its type, color, and square
  • Horizontal mirroring: the king is always mapped to files A-D (the network treats kingside/queenside symmetrically)

FullThreats (Threat features)

Encodes which pieces are threatening which squares — adding "tactical awareness" to the evaluation.

6.4 The Accumulator — Incremental Updates

The first hidden layer (1024 neurons) is called the accumulator. When a piece moves from square A to square B:

// Instead of: accumulator = weights × all_features (SLOW: 587,760 multiplications) // We do: accumulator -= weights[old_feature_index] // Subtract the moved piece's old contribution accumulator += weights[new_feature_index] // Add the moved piece's new contribution // Only 2 × 1024 additions! (fast!)

6.5 Finny Tables (Accumulator Refresh Cache)

When the king moves to a new bucket, ALL feature indices change — full refresh is needed. To speed this up, Stockfish caches accumulators per king-bucket in a table. When refreshing, it computes only the difference from the cached version.

6.6 LayerStacks

The layers after the accumulator have 8 different versions (one per material count "bucket"). This lets the network specialize: a different set of weights for middlegame vs. endgame positions.

6.7 Output Scaling

// The final eval blends two components: // PSQT = piece-square table score (from network) // Positional = positional evaluation (from network) eval = (PSQT × 125 + Positional × 131) / 128 // Then blended with material and optimism: v = (nnue × (77871 + material) + optimism × (7191 + material)) / 77871

7. Move Ordering — Why Order Matters

Alpha-beta pruning works best when good moves are searched first. If the best move is searched first, most other moves will be pruned. Stockfish's move ordering is crucial for its performance.

Move Generation Stages (MovePicker)

Moves are generated and searched in this priority order:

  1. TT Move — The move stored in the transposition table (often the best from a previous search)
  2. Good Captures — Captures sorted by SEE value + capture history
  3. Quiet Moves — Non-captures sorted by history scores
  4. Bad Captures — Losing captures (e.g., queen takes defended pawn)

History Heuristics

Stockfish maintains several tables that track which moves have been good in the past:

8. Transposition Table — Memory is Power

The transposition table (TT) is a large hash table that stores previously evaluated positions. In chess, the same position can be reached via different move orders ("transpositions"). The TT avoids re-searching these.

Structure

Each entry stores: - Key (for collision detection) - Best move found (16 bits) - Evaluation score (16 bits) - Static eval (16 bits) - Depth searched (8 bits) - Bound type (2 bits): UPPER, LOWER, or EXACT - Is PV node flag - Generation (age tracking) Organized in clusters of 3 entries per cache line (64 bytes). Default size: 16 MB (configurable up to 33 TB on 64-bit!)

Replacement Strategy

When a cluster is full, the entry to replace is chosen by comparing:

  • Depth — Prefer keeping deeper search results
  • Age — Prefer replacing entries from older searches
  • PV status — Prefer keeping PV node entries

Racy Access (Intentional!)

Multiple threads read/write the TT without locks. This means occasional data races and corrupted reads. But the performance gain from no synchronization far outweighs the cost of occasional bad data (which is detected via key verification).

9. Threading — Lazy SMP

Stockfish uses Lazy SMP (Symmetric Multi-Processing) for parallel search. Instead of complex work-splitting algorithms, it takes a beautifully simple approach:

All threads search the same position independently, but share the transposition table.

How It Works

  1. Main thread (thread 0) starts searching and controls time management
  2. Worker threads (1, 2, 3...) search the same root position independently
  3. Each thread has slightly different search parameters (thread ID affects aspiration window, LMR divisor, etc.)
  4. All threads share one global transposition table
  5. When any thread finds a better result, it ends up in the TT, helping other threads
  6. When time is up, the thread with the best overall result provides the move

Why Lazy SMP Works

  • No complex synchronization needed (no locks, no work-splitting)
  • Different thread parameters create diversity — threads explore different parts of the tree
  • The TT acts as a communication channel between threads
  • Scales well up to ~32+ threads (after that, diminishing returns)

NUMA Awareness

On multi-socket systems, memory access across sockets is slower. Stockfish replicates shared history tables per NUMA node and binds threads to specific CPUs to minimize cross-socket traffic.

10. Time Management

Time management decides how long to think. It's an art — think too long and you lose on time; stop too early and you miss a better move.

Key Factors

  • Falling eval: If the score is dropping, think longer (fallingEval factor)
  • Best move stability: If the best move keeps changing, think longer
  • Node effort: If the best move took most of the nodes, it's likely correct — stop sooner
  • Time reduction: If best move has been stable for many iterations, save time for later
  • Single legal move: If only one move is legal, spend at most 504ms

The Formula

totalTime = optimumTime × fallingEval // [0.581, 1.655] — more time if eval dropping × reduction // based on time saved from stable moves × bestMoveInstability // more time if best move keeps changing × highBestMoveEffort // less time if best move dominates node count

12. Syzygy Tablebases — Perfect Endgame Play

Syzygy tablebases are pre-computed databases containing the exact game-theoretic result (Win/Draw/Loss) for every possible endgame position with up to 7 pieces. When Stockfish reaches such a position, it can look up the perfect move instead of searching.

Two Types of Tables

  • WDL (Win/Draw/Loss): Tells you the result with perfect play. Used during search to prune.
  • DTZ (Distance to Zero): Tells you the optimal move (how many moves to a pawn push/capture that "zeroes" the 50-move counter). Used at the root to rank moves.

Integration in Search

Tablebases are probed at Step 6 of the search function, after null move pruning but before the move loop. The probe conditions are:

  • Piece count ≤ cardinality (number of pieces supported by your tablebase files)
  • 50-move rule counter = 0
  • No castling rights remaining
  • Search depth ≥ probeDepth (configurable)

PGO Build (Profile-Guided Optimization)

The strongest build. How it works:

  1. Compile with profiling instrumentation (-fprofile-generate)
  2. Run the benchmark (generates profile data)
  3. Recompile using the profile data (-fprofile-use)

The compiler can then optimize hot paths, inline frequently-called functions, and optimize branch predictions based on real usage.

14. Testing Infrastructure

Stockfish uses Fishtest — a distributed testing framework where volunteers donate CPU time to test patches. Each proposed change must pass rigorous statistical testing before being merged.

Test Types

TestTCGamesPurpose
STC (Short TC)10+0.1s~40,000Quick screening
LTC (Long TC)60+0.6s~40,000Confirm at longer time control
VLTC (Very Long TC)180+1.8s~40,000Final verification for scaling patches

Statistical Testing (SPRT)

Sequential Probability Ratio Test. Each test has bounds like [0, 5] meaning:

  • H0 (null hypothesis): Elo gain = 0 (no improvement)
  • H1 (alternative): Elo gain = 5 (meaningful improvement)
  • Games are played until statistical significance is reached
  • Typical passing rate: ~30% of submitted patches

Bench Command

./stockfish bench searches a set of predefined positions and outputs total nodes. This serves as a "signature" — if your code change doesn't affect search behavior, the node count stays the same (non-functional change). If it changes, you've made a functional change.
