Methodology & Profiling Results

The analysis was performed on macOS ARM64 (Apple Silicon) using the standard bench command (depth-limited search of 80 positions). The binary was compiled with -O3 -g -flto and profiled using macOS sample at 1ms intervals.

Key Insight: The search function itself (alpha-beta + pruning logic) dominates CPU time. NNUE evaluation is the second hotspot but is already heavily optimized with SIMD and incremental updates. The best ROI comes from reducing the number of nodes searched (better pruning/reductions) and improving move ordering (better first-move selection → more cutoffs → fewer nodes).

Improvement Proposals

P1: Enhanced Evasion Move Ordering

High Impact Low Risk
File: movepick.cpp:248-253 Category: Move Ordering Est. Impact: +5 to +15 Elo

Problem: When the king is in check, evasion moves are scored with a minimal formula: captures get PieceValue + (1 << 28) and quiet evasions only use mainHistory + contHist[0]. In contrast, normal quiet moves use 7 history components (mainHistory ×2, pawnHistory ×2, contHist[0..3,5]). This means evasion ordering is significantly worse than normal move ordering.

Why it matters: Check evasions happen in critical positions. Poor ordering causes the search to explore bad evasion moves first, missing cutoffs. In endgames and tactical positions, evasion ordering quality directly affects search depth.

Proposed change: Add continuation history [1], pawn history, and threat-escape bonuses to evasion scoring.

Current Code
else  // Type == EVASIONS
{
    if (pos.capture_stage(m))
        m.value = PieceValue[capturedPiece]
                + (1 << 28);
    else
        m.value = (*mainHistory)[us][m.raw()]
                + (*continuationHistory[0])[pc][to];
}
Proposed Code
else  // Type == EVASIONS
{
    if (pos.capture_stage(m))
        m.value = PieceValue[capturedPiece]
                + (1 << 28);
    else
        m.value = 2 * (*mainHistory)[us][m.raw()]
                + (*continuationHistory[0])[pc][to]
                + (*continuationHistory[1])[pc][to]
                + sharedHistory->pawn_entry(pos)[pc][to];
}

Rationale: This mirrors the quiet move scoring approach. Adding contHist[1] (grandparent move context) and pawnHistory (pawn structure context) gives the evasion picker much better information about which quiet evasion to try first. The 2× multiplier on mainHistory matches the quiet scoring weight. Low risk because it only affects move ordering within evasions, not pruning decisions.

P2: Nonlinear LMR Move Count Reduction

High Impact Medium Risk
File: search.cpp:1290 Category: Search Reduction Est. Impact: +3 to +10 Elo

Problem: The current LMR formula reduces based on move count linearly: r -= moveCount * 65. But the value of move ordering diminishes nonlinearly — the difference between move #3 and #4 is much more significant than between move #30 and #31.

Proposed change: Replace linear move count factor with a logarithmic decay, providing stronger reduction for very late moves while being gentler on early-but-not-first moves.

Current Code (search.cpp:1290)
r += 691;  // Base reduction offset
r -= moveCount * 65;
Proposed Code
r += 691;  // Base reduction offset
// Nonlinear: stronger reduction
// for early moves, less for late
r -= int(270 * std::log2(
         std::max(1, moveCount)));

Note: The constant 270 is calibrated so that 270 * log2(10) ≈ 897 which approximates the current 10 * 65 = 650 but with heavier weight on moves 2-5 and lighter weight on moves 20+. This needs SPSA tuning to find the optimal coefficient. The std::log2 call is cheap (single instruction on ARM64).

P3: Capture Futility with Correction Value Adjustment

Medium Impact Low Risk
File: search.cpp:1103-1111 Category: Pruning Est. Impact: +2 to +8 Elo

Problem: The capture futility pruning uses ss->staticEval as the base for futility estimation, but doesn't account for the reliability of that estimate. When the correction value is large (indicating the static eval was significantly wrong at previous positions), the futility margin should be wider. Currently, correctionValue is already computed (line ~742) but unused in capture futility.

Proposed change: Widen the capture futility margin when correction value magnitude is high, making pruning less aggressive when the position evaluation is unreliable.

Current Code
// Futility pruning for captures
if (!givesCheck && lmrDepth < 7)
{
    Value futilityValue =
      ss->staticEval + 218
      + 223 * lmrDepth
      + PieceValue[capturedPiece]
      + 131 * captHist / 1024;

    if (futilityValue <= alpha)
        continue;
}
Proposed Code
// Futility pruning for captures
if (!givesCheck && lmrDepth < 7)
{
    Value futilityValue =
      ss->staticEval + 218
      + 223 * lmrDepth
      + PieceValue[capturedPiece]
      + 131 * captHist / 1024
      + std::abs(correctionValue)
          / 163840;

    if (futilityValue <= alpha)
        continue;
}

Rationale: The correctionValue is already computed earlier in the search function (line ~742). Its magnitude indicates how much the static eval has been historically wrong in similar pawn structures. Dividing by 163840 converts the raw correction (which ranges up to ~2M) into a 0-12 cp range, making futility less aggressive in unreliable positions. The std::abs() makes it directionally agnostic — we want wider margins regardless of whether eval was too high or too low.

P4: Threat Weight Prefetching in Accumulator Update

Medium Impact Low Risk
File: nnue/nnue_accumulator.cpp:305-340 Category: NNUE / Cache Efficiency Est. Impact: +2-4% NPS

Problem: The threat accumulator update loop iterates over removed/added feature indices, loading weight columns from threatWeights[Dimensions * index] for each feature. Each weight column is 1024 × sizeof(int8_t) = 1KB, spanning ~16 cache lines. When features have non-sequential indices, these loads cause L2 cache misses.

Proposed change: Prefetch the next feature's weight column while processing the current one. This hides memory latency behind computation.

Current Loop (simplified)
for (int i = 0; i < removed.ssize(); ++i)
{
    size_t index  = removed[i];
    const size_t offset =
       Dimensions * index;
    auto* column = reinterpret_cast<
      const vec_i8_t*>(
        &threatWeights[offset]);

    for (IndexType k = 0;
         k < NumRegs; k += 2)
    {
        acc[k] = vsubw_s8(acc[k],
          vget_low_s8(column[k/2]));
        acc[k+1] = vsubw_high_s8(
          acc[k+1], column[k/2]);
    }
}
With Prefetch
for (int i = 0; i < removed.ssize(); ++i)
{
    size_t index  = removed[i];
    const size_t offset =
       Dimensions * index;
    auto* column = reinterpret_cast<
      const vec_i8_t*>(
        &threatWeights[offset]);

    // Prefetch next column
    if (i + 1 < removed.ssize())
        prefetch(&threatWeights[
          Dimensions * removed[i+1]]);

    for (IndexType k = 0;
         k < NumRegs; k += 2)
    {
        acc[k] = vsubw_s8(acc[k],
          vget_low_s8(column[k/2]));
        acc[k+1] = vsubw_high_s8(
          acc[k+1], column[k/2]);
    }
}

Note: The existing codebase already uses prefetch() extensively (TT entries, pawn history, correction history — see position.cpp:1040-1048). This follows the same pattern. The threat accumulator update (AccumulatorUpdateContext<FullThreats>::apply) accounts for ~318 samples (3.2% of CPU time). Even a 10% improvement in this hot loop = ~0.3% overall NPS gain. Similarly add prefetch to the added loop and to the update_threats_accumulator_full function.

P5: Consolidated TT Probe Loop

Low Impact Low Risk
File: tt.cpp:222-240 Category: NPS / Code Efficiency Est. Impact: +0.5-1% NPS

Problem: The TT probe function currently uses two separate loops: one to search for a key match (3 iterations), and on miss, another to find the best replacement candidate (2 iterations starting from index 1). For misses, this means iterating over the same 3 entries twice, loading depth8 and relative_age() in the second pass even though they were available in the first pass.

Proposed change: Track the best replacement candidate during the initial key search loop, eliminating the second pass entirely.

Current (two loops)
for (int i = 0; i < ClusterSize; ++i)
    if (tte[i].key16 == key16)
        return {tte[i].is_occupied(),
                tte[i].read(),
                TTWriter(&tte[i])};

// Second loop for replacement
TTEntry* replace = tte;
for (int i = 1; i < ClusterSize; ++i)
    if (replace->depth8
        - 8*replace->relative_age(gen)
      > tte[i].depth8
        - 8*tte[i].relative_age(gen))
        replace = &tte[i];
Proposed (single loop)
TTEntry* replace = tte;
for (int i = 0; i < ClusterSize; ++i)
{
    if (tte[i].key16 == key16)
        return {tte[i].is_occupied(),
                tte[i].read(),
                TTWriter(&tte[i])};

    if (  replace->depth8
        - 8*replace->relative_age(gen)
      >   tte[i].depth8
        - 8*tte[i].relative_age(gen))
        replace = &tte[i];
}

Note: All 3 entries are in the same 32-byte cache line (already fetched), so the cache benefit is minimal. The gain is from eliminating branch overhead and redundant field reads on misses. TT probe accounts for only ~0.5% of CPU time, so the absolute impact is small. However, this is a clean code improvement with zero risk.

P6: qsearch Move Count Threshold Tuning

Medium Impact Medium Risk
File: search.cpp:1666-1668 Category: Pruning / qsearch Est. Impact: +2 to +7 Elo

Problem: In qsearch, the move count pruning threshold is a fixed moveCount > 2. This means in qsearch, after the TT move and 2 additional captures, all remaining non-checking captures are pruned. However, this threshold doesn't account for whether we're in a rich tactical position (many captures available) or a quiet one.

Proposed change: Scale the threshold by the futility base relative to alpha. When the position is much better than alpha (high futility base), we can prune more aggressively. When close to alpha, allow more moves.

Current Code
if (moveCount > 2)
    continue;
Proposed Code
if (moveCount > 2
    + (futilityBase < alpha + 200))
    continue;

Rationale: When futilityBase (staticEval + 328) is close to alpha, we're in a position where material gains matter more, so allowing one extra capture to be searched can find important tactical sequences. The condition futilityBase < alpha + 200 evaluates to 0 or 1, effectively making the threshold 2 or 3. This is a safe, tunable change. qsearch accounts for ~8% of CPU time, so even small improvements compound.

P7: Adaptive Singular Extension Margin

High Impact Medium Risk
File: search.cpp:1177 Category: Search Extensions Est. Impact: +5 to +15 Elo

Problem: Singular extension uses a fixed formula for its beta: singularBeta = ttValue - (60 + 66 * (ttPv && !PvNode)) * depth / 55. This doesn't adapt to the complexity of the position. In simple endgames with few legal moves, a move is more likely to be truly singular, so the margin should be tighter (extending more often). In complex middlegames, moves are less likely singular.

Proposed change: Scale the singular margin by the number of pieces on the board. Fewer pieces → tighter margin → more extensions.

Current Code
Value singularBeta =
  ttData.value
  - (60 + 66 * (ss->ttPv && !PvNode))
    * depth / 55;
Proposed Code
int pieceFactor =
  51 + pos.count<ALL_PIECES>();
Value singularBeta =
  ttData.value
  - (60 + 66 * (ss->ttPv && !PvNode))
    * depth / pieceFactor;

Details: With 32 pieces (opening), pieceFactor = 83 → margin is wider than current (less extension). With 6 pieces (endgame), pieceFactor = 57 → margin is tighter (more extension). The constant 51 is chosen so the formula behaves similarly to the current code at typical middlegame piece counts (~14 pieces → pieceFactor ≈ 65, close to current 55). Needs SPSA tuning for the base constant.

P8: Continuation History Depth-Decay in Scoring

Low Impact Low Risk
File: movepick.cpp:228-234 Category: Move Ordering Est. Impact: +1 to +5 Elo

Problem: In quiet move scoring, all 5 continuation history tables (contHist[0..3, 5]) are weighted equally. However, contHist[0] (parent move context) is far more predictive than contHist[5] (6 plies back). The equal weighting dilutes the signal from the most relevant history.

Proposed change: Apply a weighting scheme that emphasizes recent context.

Current Code
m.value += (*continuationHistory[0])[pc][to];
m.value += (*continuationHistory[1])[pc][to];
m.value += (*continuationHistory[2])[pc][to];
m.value += (*continuationHistory[3])[pc][to];
m.value += (*continuationHistory[5])[pc][to];
Proposed Code
m.value += (*continuationHistory[0])[pc][to];
m.value += (*continuationHistory[1])[pc][to];
m.value += (*continuationHistory[2])[pc][to] * 3/4;
m.value += (*continuationHistory[3])[pc][to] / 2;
m.value += (*continuationHistory[5])[pc][to] / 2;

Rationale: contHist[0] and [1] (parent and grandparent context) are the most reliable predictors. contHist[2..5] decay in relevance. Integer division by 2 and multiplication by 3/4 are cheap (shift/add). This slightly reshapes the quiet move scoring to prioritize recent contextual information. Needs empirical testing — the exact decay constants should be SPSA-tuned.

Testing & Validation Strategy

Each improvement must be validated independently. Stockfish uses a rigorous testing methodology based on SPRT (Sequential Probability Ratio Test) via the Fishtest distributed testing framework. For local testing, we use these approaches:

1. Bench Signature

  • Run ./stockfish bench
  • Verify binary produces valid output
  • Compare NPS (higher = better)
  • Node count will change (expected)

2. Self-Play Testing

  • Use cutechess-cli for matchplay
  • Minimum 1000 games at STC (10+0.1)
  • Compare against unmodified baseline
  • SPRT bounds: [0, 5] Elo at 95% CL

3. Regression Checks

  • Run tests/perft.sh (move gen)
  • Run tests/signature.sh
  • Ensure no test failures
  • Check for crashes in edge cases

Local Validation Commands

# 1. Build modified version
make clean && make build ARCH=apple-silicon -j8

# 2. Run bench (quick NPS comparison)
./stockfish bench 2>&1 | tail -3

# 3. Compare node counts (search behavior changed?)
diff <(./stockfish_baseline bench 2>&1 | grep "Nodes searched")  \
     <(./stockfish bench 2>&1 | grep "Nodes searched")

# 4. Self-play with cutechess-cli (if available)
cutechess-cli \
  -engine name=baseline cmd=./stockfish_baseline \
  -engine name=modified cmd=./stockfish \
  -each tc=10+0.1 proto=uci \
  -rounds 1000 -pgnout results.pgn \
  -sprt elo0=0 elo1=5 alpha=0.05 beta=0.05

Risk Analysis

Low Risk — P1, P3, P4, P5, P8

These changes are additive or affect only move ordering/margins, not the fundamental search tree structure. P1 adds more history info. P3 widens a margin. P4 adds prefetch hints (no-op if wrong). P5 is a refactor with identical behavior. P8 rescales existing values. None can cause crashes or correctness issues.

Medium Risk — P2, P6, P7

These change the search tree shape: P2 alters reduction amounts (could over/under-reduce), P6 changes qsearch pruning (could miss tactics or search too many nodes), P7 changes extension behavior (could cause search explosions in endgames). All need self-play testing. Worst case: revert the change.

Correctness Risk — None

All proposals preserve the correctness of the search algorithm. No change affects move legality, repetition detection, or mate scoring. The engine will still play legal chess regardless of parameter values.

Interaction Risk — P2 + P7

LMR changes (P2) and singular extension changes (P7) interact: both affect the effective search depth. If both are applied, they should be tested together as well as individually. Other proposals are independent.

Implementation Timeline

Phase 1: Quick Wins

Implement P1 (evasion ordering), P5 (TT probe), and P3 (capture futility correction). These are the safest changes with immediate measurable impact. Build, bench, and verify NPS.

Phase 2: NPS Optimizations

Implement P4 (threat weight prefetching) and P8 (contHist decay). Profile before and after to verify NPS improvement. These don't change search behavior, only speed.

Phase 3: Search Tuning

Implement P2 (nonlinear LMR), P6 (qsearch threshold), and P7 (adaptive singular extension). Each needs individual testing via self-play. Apply one at a time, bench after each.

Phase 4: Integration & Validation

Combine all successful changes. Run full bench suite. Compare overall NPS and search quality against the unmodified baseline. Document results.

Expected Outcome: The combination of improved move ordering (P1, P8), smarter pruning (P3, P6), better reductions (P2), and enhanced extensions (P7) should produce a measurable improvement in both NPS and search quality. Conservative estimate: +10 to +30 Elo combined (subject to self-play testing validation). NPS improvement from P4 and P5: +2 to +5%.
